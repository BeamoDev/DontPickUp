# Click, carry and throw

Tag a small brick/prop BasePart or whole Model with exact lowercase `throw`. Names do not activate behavior. Click once to pick it up, then click again to launch. On touch, each activation is a short stationary tap; dragging the camera does not throw or drop a held item. E and controller RT follow the same two-press behavior. Q/B cancels.

Carried props follow the view at a fixed server-chosen offset about 3.2 studs ahead of the head. The client sends only a token and a changed unit direction, at most 20 times per second while holding. The server independently validates/rate-limits aim, derives the position, checks wall occlusion and follows using a critically damped spring in its single active holding heartbeat. Pickup starts at the existing prop pose, preserving its rotation relative to the holder; release launches from the current smoothed pose. The spring keeps velocity continuous between aim updates and reuses per-hold raycast parameters. Both target and smoothed positions are checked for walls. The actual server world prop moves, so all clients receive the carried position; the holder additionally sees a local cosmetic copy updated after the camera each render frame, avoiding replication stepping while turning. It accepts no client position, force, speed or charge.

The second activation launches at 36 studs/second plus four studs/second upward. Speed does not depend on holding time. A narrow white trail follows briefly; there is no extra particle burst. World collisions and server-owned physics remain enabled after launch. Authored effects/welds are preserved; only generated trail attachments/temporary collision constraints are cleaned up.

Reservations are per-player/per-prop and release/cancel/aim use the server-issued token. A second click before the grab reply queues one release. Mouse release alone never launches. Menus, focus loss, death, seating, tag removal, teardown, loss of eligibility or a 30-second hold expiry cancel safely. No damage, rewards or prop respawn is introduced.

`GShared/Interaction/ThrowConfig` owns public limits and speed. ThrowController owns local carry input and aim updates; InteractionController routes one input event; ThrowService owns admission/range/reservation/physics; ThrowEffects owns the short white trail. The Game bootstrap creates `DontPickUpGameNet.ThrowAim` in addition to the validated Request RemoteFunction.

Impact debris and all impact touch listeners have been removed. Only the existing white trail remains, with owned effect cleanup after 1.1 seconds.

`GClient/Interaction/CarryView` hides the real carried parts locally and renders an anchored, non-collidable, non-querying copy. It smooths pickup and free-cursor aim in camera-local coordinates, so fast turns retain the settled hold offset instead of chasing a delayed world-space point. It uses current-frame aim and bounded wall queries. Cancellation restores every saved local transparency and destroys the copy. On release, the same cosmetic copy immediately follows the configured launch speed, gravity and spin, then blends over 0.18 seconds into the real replicated flight after server acceptance and launch state arrive. It never moves or takes ownership of server parts. The cosmetic flight stops on an obstruction, and a missing receipt is bounded to 0.75 seconds. Other clients continue to see the authoritative server prop. No extra remote frequency or per-object render connection is added: GameController calls ThrowController from the existing post-camera update.
